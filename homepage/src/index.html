QKiSS

An unsolicited renaissance of KiSS

QKiSS is a modern implementation of KiSS viewer in Qt 6, compatible with KISS/GS and FKiSS 1 & 2 specifications.

Download GitHub GitLab

Free software under GPLv3 · Linux · Windows

What is KiSS?

KiSS (Kisekae Set System) is a format of digital paper dolls. You dress the characters up by dragging their clothes with the mouse, and FKiSS scripts add interactions such as animations and sounds.

“Kisekae” comes from the Japanese word “着せ替え人形” (pronunciation: “kisekae ningyou”), meaning “dress-up dolls”.

KiSS originated from Japanese otaku subculture and personal computer enthusiasts community (particularly those using the NEC PC-9800 series) in the 1990s, and gained popularity throughout the 1990s and early 2000s.

Why QKiSS?

By 2024, the existing KiSS viewers for Linux had stopped working: fkiss can still be built but no longer runs, and GnomeKiSS depends on outdated GNOME 2 libraries that most distributions no longer ship. Inspired by both, QKiSS was built from scratch.

Yes, I know there are some KiSS implementations which can run in a Web browser by using Web technologies directly, but they are (technically and architecturally) ugly when you want to turn them into a desktop application integrated with your OS and file system; I'm also tired of writing lots of disgusting HTML / CSS / JS as a workaround to make a web page pretend to be a native application, and then pack it into a bloated blob of an executable; and such a thing which actually can be done in a light-weight way should not need a browser at all, nor some Chimera like Electron. Similar reasons also apply to Java, which runs unbearably slow.

Besides, it was also a chance to practice writing a somewhat sizable project in C++. After all, it really is quite fun to write. (Although by the time I finished, this world of LLMs no longer seems to need a loser like me to write programs: the kind who grinds LeetCode for three months, then starts wishing to be reincarnated in another world.)

This project comes from nostalgia for the Windows 95/98 and GTK+ 2 era —— a lost age before Internet was polluted by AI-generated junk (this project does use some AI though). After all, life is frightening enough as it is; the real world is a hot mess, while nijigen and isekai remain a pure promised land.

Highlights

  • Full-featured, with a handy UI

    • Switch files quickly from the side panels: the sets in your folders, and the CNF files inside an archive.
    • Read the CNF, with syntax highlighting.
    • Read the docs bundled with a set.
    • Read CNF files and docs written in Shift-JIS, with no garbled text.
    • Observe objects: point at any part of a doll to see its cel, object and position.
    • Check the log, which points out problems down to the line.

  • Faithful to the specs, faithful to the users

    • Implements the KISS/GS base specification, and an interpreter for the interactive scripts of FKiSS 1 & 2 (in tests, 90% of Japanese KiSS sets run fine).
    • FKiSS 3 & 4 have too few sets, almost none of them by Japanese KiSS artists, so they were not worth the bother.
    • One-click unfix: who wants to sit there clicking a fixed item over and over? Playing shouldn't feel like work.
    • No Electron, which no user likes (these Weblins*1 who use Electron to dress up web pages as native apps seem to think your RAM is free).

  • The romance of engineering and aesthetics

    • The code of the main program is handcrafted, without LLM agents*2 (and is probably the author's last hand-written software project, so cherish it while it lasts).
    • Linux is no longer a second-class citizen (Windows is).
    • Open source and automated builds make sure nothing weird is inside.
    • Tango-style UI icons take you back to the 2000s.
    • An AppArmor profile for tinfoil-hat security nerds*3 who get a braingasm whenever the LSM spits out a DENIED audit log.
    • Built with Qt 6 / C++ 20, without caring about old systems.

    Q&A

    Which versions of FKiSS does QKiSS support?
    • KISS/GS (General Specification), with its extended comments.
    • FKiSS (the script language): versions 1 and 2.

    That is quite enough to load nearly all the Japanese KiSS sets I could find on the Internet.

    But the shell() command is not implemented, on purpose, to avoid any security hole.

    Can QKiSS be ported to macOS?

    I have no Mac. So, no idea.

    Why the name “QKiSS”?

    A KiSS viewer implemented in Qt 6. Having “KiSS” in the name is a convention of KiSS viewers, like fkiss, GnomeKiSS, KISSLD, and Direct KiSS.

    I also considered a few other names:

    • QtKISS: pronounced the same as “Cute Kiss”, and named with the same logic as GnomeKiSS: “platform name + KiSS”. Well, actually, QKiSS had this name in the early days of development. But according to the fair use rules of the Qt trademark, the Qt name may only be used “where the Qt name is not being used in a way which suggests sponsorship or endorsement of the product”. To avoid someone giving me crap about it someday, I had to rename it.
    • Qute KISS: also pronounced “Cute Kiss”, but argh… Qute is a trademark of a Japanese computer game company. Too risky.
    Where can I find KiSS sets to open?

    The biggest archive right now is probably Otaku World, though you have to dig through it patiently. It has sets by both Japanese and Western artists.

    Some people have also written their own implementations, such as one in JavaScript or one in Haskell, with online demos you can open right in your browser. But most of the sample sets they provide were dug up from Otaku World, too.

    Note that these KiSS sets may contain NSFW content, and I can't make any guarantees.

    What security measures are there for the LZH format and external programs such as lha?

    LZH / LHA is a free compression format and tool, developed in 1988 by Haruyasu Yoshizaki, a Japanese physician. It was very popular in the Japanese personal computer scene of the time (by comparison, PKZIP, the ZIP tool that later became the mainstream, did not appear until 1989, and was shareware), so the KiSS developer community, which originated in Japan, naturally adopted LZH to compress KiSS sets.

    But today, both the format and its implementations are old, and lha and unar extract LZH files of unknown origin, which makes them the easiest target for a malicious file. So on Linux, QKiSS locks them up:

    • Landlock: they can read only the system files and the archive being opened, nothing else in your home folder, and they can write nowhere except unar's temporary folder.
    • seccomp: high-risk system calls such as io_uring, sockets and namespaces are turned off.
    • AppArmor (the optional qkiss-apparmor package, Debian / Ubuntu / openSUSE only): lha and unar are restricted once more, and QKiSS itself cannot read secrets such as ~/.ssh, nor write files used for persistent attacks, such as ~/.bashrc.

    Landlock and seccomp are built into QKiSS, with nothing to install, but they cover only these two external programs, not QKiSS itself.

    As for Windows: as Eisen once said, anyone who uses Windows is a brave warrior, and needs none of these little tricks.

    Why is only AppArmor supported? Is there no SELinux support?

    It doesn't fit the use case. SELinux's security model is inherently bad at “deny access to a few folders such as ~/.config/autostart, and allow access to everything else”, and I can't force users to put their KiSS LZH files only into some hardcoded ~/qkiss folder.

    Besides, on the Linux desktop, people who deliberately run GUI apps outside unconfined_t must be rare. Such people either work at the Pentagon*1, or moved to Qubes OS long ago.

    One more thing: I'm allergic to the taste of SELinux's command names. getenforce, chcon, load_policy, restorecon and a pile of other commands refuse to have an se prefix, and crap all over /sbin/. If writing this in my free time got me a work injury, there would be no insurance payout.

    But even if you use SELinux, you still have the protection of Landlock and seccomp, which covers only the extraction by the two external programs, lha and unar.

    *1 Generally speaking, playing any kind of KiSS viewer in the workplace is not recommended.

    Why not Rust?
    • I'm a KDE user, and Qt feels the most seamless to use.
    • Qt Widgets is mature and stable: its major versions last for years, with few API breaks. I don't have to build any widgets myself, and I can get 80% of the features done with hardly any third-party libraries.
    • Rust would need a binding, and then I'd have to worry about its API breaks, its quality and its extra pitfalls, plus the Qt C++ patterns that don't translate directly into Rust. I'd have two things to keep up with, Qt and the binding, and I'd lose all the help from Qt Creator.
    • I want to practice C++.
    Did you use AI (LLMs)?
    • This project does use help from LLMs, but keeps it under control as much as possible, with various engineering methods (e.g. isolation in KVM virtual machines, and reviewing commits by hand).
    • LLM agents (e.g. Claude Code, Codex) were used only for the translations, this website and CI/CD.
    • No damn vibe coding, ever, in the main program (Qt / C++) or in the Python code. Even with help from LLMs, the code was reviewed and modified by hand, line by line: I can understand and explain every line of it. I also proofread the translations by hand, as much as my broken foreign languages allow.

    Have you noticed the style of the icons on this website?

    It is a style of icon design for graphical user interfaces called Tango Desktop*1, proposed by freedesktop.org and popular around 2005–2010. If you used some free software back then, you may have seen it.

    For the 2000s aesthetic romance of Tango-style UI icons, and to bring realistic icons back to a world where flat UIs and monochrome icons, an arbitrary, trend-chasing design fad that never thinks of people with dyslexia, blow around like an ill wind*2, I ended up making the Tango Remixer project on the side, so I could easily stuff Tango icons into Qt projects like QKiSS and keep their look consistent across platforms; then I also took on maintaining three XDG-compatible icon theme packs from the 2000s. Then my OCD couldn't stand making the app public before its icons were pretty, so it took one more year...

    As it turned out, developing Tango Remixer, and sorting out, fixing and drawing a pile of extra tango-flavoured icons, came, without exaggeration, close to taking longer than developing QKiSS itself. That is why QKiSS, started in August 2024, was only first released in October 2026...
